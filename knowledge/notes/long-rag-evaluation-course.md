# 检索增强生成与评测长笔记

## 问题建模

检索增强生成把知识定位与语言生成拆成两个阶段。用户问题先转成检索请求，从受控语料得到证据，再把有限证据交给模型回答。它解决的不是模型“知道一切”，而是让回答能引用更新、更私有、更可核查的数据。设计前要区分事实问答、操作指引、跨文档综合和开放建议，因为不同任务的分块、召回数量、重排与成功标准不同。若问题本身需要外部实时信息，本地笔记检索不应伪装成完整答案。

## 文档摄取

摄取阶段读取文档、校验编码和大小、提取结构，再生成稳定 chunk。Markdown 天然包含标题层级，按标题分块通常比固定字符窗口更能保持语义边界。表格、代码块和列表不应被任意截断。每个 chunk 保存 source path、heading、start_line、end_line、file_hash 和 chunk_id。file_hash 用于增量更新和证据验证；稳定 chunk_id 便于追踪同一段在不同评测中的表现。删除文件时索引也必须删除对应记录。

## 分块权衡

分块太小，召回结果缺少上下文，定义与限制条件可能分离；分块太大，相关词虽命中，但大量无关文本消耗 token。常见方案是按标题分块，再对超长章节按段落或 token 二次切分，并保留少量重叠。重叠能减少边界损失，却会导致重复证据和分数偏置。评测应尝试多个 chunk size，而不是凭感觉选择。对于代码仓库，函数、类和文件结构比自然语言段落更合适。

## 稀疏检索

倒排索引记录 token 到文档的映射。TF-IDF 与 BM25 使用词频和逆文档频率，让稀有术语获得更高权重。BM25 还做词频饱和与长度归一化，避免长文档仅因出现次数多而统治结果。中文文本缺少空格，可使用分词器；小项目使用汉字 unigram/bigram 是可解释基线。错误码、API 名、类名、路径等精确词通常是稀疏检索强项。搜索结果要稳定排序，分数相同时按路径和行号，方便复现测试。

## 语义检索

Embedding 能召回词面不同但语义接近的内容，例如“上下文压缩”和“减少提示 token”。它需要选择模型、维度、距离函数和向量存储，还要考虑模型升级后的全量重建。向量相似不保证事实相关：通用概念相近的段落可能缺少问题要求的具体条件。隐私敏感笔记若调用云端 embedding，需要明确数据是否离开本机。没有语义评测集时，先建立 BM25 基线通常更稳妥。

## 混合检索与重排

混合检索分别取得稀疏和向量候选，用 Reciprocal Rank Fusion 等方法合并，再用 cross-encoder 或大模型对前几十条重排。重排器能结合完整问题判断相关性，但增加延迟和成本。工程上应记录每一阶段候选，才能知道遗漏发生在初召回还是重排。高风险答案可以提高召回数，再让上下文管理去重；低延迟交互则限制候选与重排数量。任何策略都需要固定任务集比较。

## 查询改写

用户长问题可能包含背景、约束和多个子问题。查询改写可提取核心名词、生成同义词或拆分多个检索查询。LLM 改写可能引入原问题没有的概念，因此要保留原始查询，并把改写视为额外候选来源。中文 bigram 基线能直接处理许多自然句，不必每次依赖模型。跨文档任务可先生成子问题，分别检索后合并证据，但要限制数量，避免查询爆炸。

## 证据打包

上下文打包不仅是截断字符串。每条证据应以路径、行号、标题开头；先按相关性与来源多样性排序，去掉高度重复块，再放入预算。若某块超过剩余预算，优先保留与查询最相关的句子，而不是机械保留开头。full 策略使用命中文档完整内容作为成本基线；relevant 只放高分块；summary 对长块先压缩。摘要必须保留来源坐标，并明确是抽取式还是模型生成式。

## Token 预算

字符估算适合无模型依赖的预检查：英文约四字符一个 token，中文往往更接近一字一 token，但不同 tokenizer 差异很大。API 返回 usage 时必须优先记录真实值，并注明 provider_usage；本地估算标记 estimate。总预算包括系统提示、历史消息、工具 schema、工具结果和预留输出，不只是检索文本。工具调用循环每一步都要累计，超过总上限应停止并给出可解释错误。

## 生成约束

总结提示要求模型只依据证据、证据不足时拒答、引用路径行号。提示只是软约束，输出后仍要做引用校验。答案中的每个引用必须属于本次检索证据；更严格时重新读取文件并验证引用行附近包含被引用事实。模型可能给出正确结论但错误引用，因此要点正确率与引用准确率分开。对于无证据回答，系统可以标记 unsupported，而不是把流畅度当作正确性。

## 检索评测

检索评测需要给每个问题标参考 chunk 或参考文件。Recall@K 衡量参考证据是否进入前 K；Precision@K 衡量候选中相关项比例；MRR 关注第一个相关结果排名；nDCG 能处理多级相关性。只有四篇短文时指标容易饱和，不能代表真实规模。知识库应有长短文、相似主题、同义表达和干扰段落。增量索引还要测试修改、删除与编码异常。

## 回答评测

规则评测可检查期望要点、禁止内容、引用合法性与错误分类，成本低且可重复。LLM-as-judge 可评估表达和部分语义，但评审模型也有偏差，应固定版本、提示和温度，并保留抽样人工复核。成功阈值应在任务中声明，例如至少命中五个要点中的三个且全部引用合法。不能把“检索非空”当作回答成功，因为无关证据同样非空。

## 失败用例

评测必须包含空查询、非法 top_k、路径穿越、绝对路径、非 Git 仓库、Git 超时、GitHub 404、权限不足、限流、命令超时、敏感环境读取、Python -c 和 Git 写操作。失败用例不追求 ok=true，而追求正确拒绝与正确 category。若 expected permission 实际返回 transient，Agent 可能无意义重试；若超时被标 parameter，又会失去恢复机会。错误分类本身是系统能力。

## 模式对比

single Agent 拿全部工具，自主决定调用，路径短但权限面大；delegated 模式让主 Agent 拆任务，检索子 Agent 只读，总结子 Agent 无工具，控制更强但调用更多。比较时保持模型、问题集、策略和预算一致。记录每个 Agent 的 token 与耗时，不只记录总数。策略矩阵可以裁剪：先在 delegated 下比较 full/relevant/summary，再用最佳策略比较 single/delegated，避免不必要的 API 成本。

## 数据泄漏

评测任务和知识库之间要防止答案泄漏。如果笔记直接写“问题 X 的答案是 Y”，指标只说明字符串匹配。真实课程笔记应围绕技术主题自然组织，任务从内容中提出。用于调参的问题集与最终测试集分离。公开数据集只提交少量样本、来源和生成脚本，不把大型原始数据复制进仓库。私有笔记不应进入公开 Git。

## 报告可复现

报告记录时间、commit、模型、供应商、模式、策略、任务数、预算和环境。指标包含成功率、要点命中率、引用准确率、平均输入输出 token、P50/P95、工具调用、重试和失败分布。原始逐题结果保留，便于分析失败。文档表格应由 reports JSON 生成，不能手工写漂亮数字。没有 API Key 时明确写“本地模式，不可用于简历模型指标”。

## 线上监控

离线评测不能覆盖真实请求分布。线上应监控零命中率、用户改写率、引用点击、工具错误、延迟和成本，并按知识域切片。隐私要求下只保存脱敏查询或聚合。发现某类问题失败后，先加入可复现任务，再修检索、提示或工具。没有回归集的“快速修复”容易让另一类问题退化。评测集因此既是测量工具，也是工程记忆。

## 实践路线

第一阶段建立可解释关键词或 BM25 基线、来源行号和十几条固定任务；第二阶段增加中文切分、Markdown 分块和增量索引；第三阶段加入向量召回与重排，用同一评测比较；第四阶段优化上下文摘要和模型工具调用；最后才考虑分布式索引与大规模缓存。每一步都保留旧基线和真实报告，能说明为什么新复杂度值得，而不是为了技术名词堆栈。
