# Agent 工程课程长笔记

## 一、从任务边界开始

Agent 工程首先不是选择模型，而是定义任务边界。一个任务要说明输入是什么、允许读取哪些数据、能调用哪些能力、完成条件是什么，以及失败后由谁接管。边界不清时，模型的灵活性会放大歧义：同一句“整理项目”可能意味着只读总结，也可能意味着重写文件、提交代码甚至发送消息。工程系统应把授权转化为工具集合与参数策略，把完成条件转化为可执行校验，而不是在系统提示里写一句“请小心”。任务接入阶段还应生成 trace_id，记录调用来源和预算，让后续步骤都能关联到同一个任务。

## 二、规划与执行分离

规划决定下一步做什么，执行负责让动作真实发生。二者分离后，可以让模型提出工具名和参数，由确定性代码检查 schema、权限、幂等性和审批条件，再交给 MCP Client 调用。执行结果必须视为不可信数据：它可能包含提示注入、格式错误、过长文本或与任务无关的信息。规划器不应拥有绕过工具直接访问操作系统的后门。对于固定、重复、风险较高的流程，确定性编排往往比完全自主规划更适合；对于开放问题，可以在有限工具、最大步数和总预算内允许模型动态选择。

## 三、工具契约不是函数签名

函数签名只说明参数类型，工具契约还要解释使用时机、返回数据、错误类别、副作用和可重试性。比如 file_access 的 path 是相对于授权工作区的路径，不是任意绝对路径；write 的 create 与 overwrite 表达不同意图；expected_sha256 用于检测读取后文件被其他进程修改。工具描述既服务于模型选择，也服务于人工审查。错误应放入稳定结构，parameter 表示修正参数，permission 表示需要新的授权，conflict 表示重新读取并重新规划，timeout 与 transient 才可能有限重试。

## 四、上下文不是越多越好

模型上下文具有容量和成本上限。把五个命中所在文档全部拼接，召回可能较高，但无关段落会稀释注意力；只给一行摘要成本低，却可能丢失定义条件和例外。full 策略适合作为基线：把命中文档完整内容按预算放入；relevant 策略按分块相关性选择；summary 策略先保留来源标识，再压缩较长块。裁剪顺序应可解释：先丢低分块，再压缩单块正文，最后在句子边界截断；路径、标题和行号优先保留，因为它们用于引用验证。

## 五、检索质量要独立测量

最终回答不正确，原因可能是没找到证据，也可能是模型没有正确使用证据。把检索与总结拆开，才能分别测 Recall@K、MRR、要点命中率和引用准确率。中文关键词检索需要分词；简单项目使用汉字 bigram 能覆盖许多连续短语，大型系统可加入 BM25、Embedding 与 reranker。索引要支持增量更新，否则每次查询全量扫描会随笔记数量线性变慢。每个 chunk 应保存路径、标题、起止行、内容哈希和稳定标识，查询结果还要重新对照原文，避免索引陈旧。

## 六、Verification Loop

调用返回不等于任务完成。可靠流程是执行、验证后置条件、分类失败、决定重试或回退、记录每次尝试。文件写入的后置条件是目标字节与预期一致；Git 查询的后置条件是进程成功且输出可解析；CI 返回必须包含合法状态枚举；检索证据必须能回到真实文件；命令工具则验证 exit_code、stdout 和 stderr 结构。重试采用指数退避与抖动，并受总截止时间约束。回退要显式标记，例如 GitHub Actions 不可用时返回本地记录，并注明 stale，而不是假装数据仍然实时。

## 七、幂等性与副作用

读操作通常适合重试，但也要考虑外部 API 限流。写操作能否重试取决于幂等设计。覆盖写相同字节近似幂等，但“追加一行”“发送邮件”“创建订单”会产生重复副作用，需要幂等键或禁止自动重试。命令执行尤其不能仅凭命令名判断安全：git status 与 git reset 都使用同一个可执行文件；python 脚本可以访问进程权限范围内的任何资源。本地执行要用参数级策略，真正隔离则依赖容器或操作系统沙箱。

## 八、子 Agent 的价值与成本

子 Agent 不是把函数换一个名字。检索子 Agent 应只有读取证据所需工具，并输出路径、行号与摘录；总结子 Agent 不拥有工具，只能基于证据写答案。这样可以缩小权限、降低提示注入传播、分别评测召回和生成。但委派也会增加提示、序列化、网络和协调开销。比较 single 与 delegated 时，要使用同一问题集、模型、预算和温度，分别记录每个 Agent 的输入输出 token、耗时与工具调用次数。若没有真实模型数据，只能报告本地流程可运行，不能宣称委派提升了准确率。

## 九、可观测性数据模型

Task 保存原始问题、模式、策略、状态和最终答案；Step 表示接入、规划、检索、上下文、总结与回写；ToolCall 保存脱敏参数、caller、工具名、结果与 trace_id；Attempt 保存每次执行的耗时、结果、错误类别和退避。这个层级既能还原单次故障，也能聚合出工具乘错误分类乘时间窗口的分布。日志不应记录 API Key、Authorization、密码和完整用户文件。SQLite 适合单机演示，生产环境可把 trace 发往 OpenTelemetry 或集中日志系统。

## 十、模型工具调用循环

模型先看到 tools/list 转换出的函数定义，然后生成 tool_calls。Host 校验并通过 MCP Client 执行，把结构化结果作为 tool message 回填，再让模型继续。循环必须限制最大步骤、总 token、单次工具结果大小和取消信号。模型请求不存在的工具、参数 schema 不合法或触发权限错误时，应把结构化错误回填给模型修正，而不是服务端静默替它猜参数。最终回答中的引用需要与本次证据集合比对，禁止引用未调用过的文件。

## 十一、结果回写

结果回写不是只写一条 metrics。一个可审计任务应把问题、答案、引用、模式、策略、token、耗时和验证状态写入授权工作区。回写本身也应通过同一个 MCP file_access，而不是 Agent 直接 import Service，这样路径沙箱、备份、原子写和调用日志都会生效。文件名使用日期、可读标题和短随机标识，避免并发覆盖。若回写失败，任务可以返回答案，但状态必须明确标注未持久化。

## 十二、评测与诚实陈述

评测任务需要覆盖中文问答、跨笔记综合、Git、CI、文件操作、命令执行和故意失败。成功定义不能是“有输出”：问答要满足要点阈值与引用校验，越权测试要得到 permission，超时测试要得到 timeout。报告至少包含成功率、要点命中率、引用准确率、平均 token、P50/P95 延迟、工具调用和重试次数。每份报告写明模型、日期、任务数和代码版本。没有 API Key 时运行本地模式只是回归测试，不能把数字包装成大模型效果。

## 十三、安全优先级

最优先的是缩小能力：只暴露需要的工具，只挂载授权目录，只传最小环境，只允许只读 Git 子命令。第二层是输入校验和路径规范化，第三层是运行时资源限制，第四层是审计与告警。Prompt 中的规则属于补充，不能替代代码边界。密钥只在请求内存或服务端环境变量存在，不返回浏览器，不写 SQLite，不进入异常消息。外部返回内容应标记为数据，必要时在进入模型前做长度限制与注入检测。

## 十四、渐进式交付

工程改造应小步提交。先保留现状快照，再为已知问题写失败测试，然后修改实现。工具契约、验证回路、安全、索引、Agent 和 API 分开提交，便于 code review 和回滚。Windows 本地与 Ubuntu CI 都要跑，路径、信号、进程树和 Docker 挂载尤其需要双平台测试。文档由真实 schema 和真实报告生成，避免代码已经变化而 README 仍然描述旧行为。演示时先展示工具发现，再展示成功路径、越权拒绝、超时分类、回退和 trace 查询。
